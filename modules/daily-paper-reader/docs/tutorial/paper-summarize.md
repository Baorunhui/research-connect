# 论文总结链路说明

本页讲解「论文总结」功能的完整流程：一篇论文从你贴进来的链接/上传的 PDF，
到生成一张与日报纸张页同构的阅读页，中间经过哪些阶段、每个阶段用什么技术。

## 整体流程

「论文总结」由本地后端（`python src/local_server.py`）驱动，核心思路是
**复用日报流水线的 Step 6 文档生成能力**，而不是另起一套独立链路：

```
输入（arXiv/网页链接 或 上传 PDF，≤50MB）
   ↓
抓取正文（三选一）
   ├─ arXiv 链接 → Atom API 取元数据 + 下载 PDF 备用抽图
   ├─ 普通网页   → HTML 解析提取标题与正文
   └─ 本地 PDF   → PyMuPDF 全文解析
   ↓
缓存检查（arXiv ID 或 PDF 内容哈希为 key）
   ↓
复用日报文档生成（generate_external_paper_docs，精读模式）
   ├─ 速览五段（tldr/motivation/method/result/conclusion）
   ├─ 图表抽取（PaperCropper + Docling → PyMuPDF 兜底）
   ├─ 图表解读（纯文本模型批量解读）
   ├─ 标题摘要翻译成中文
   └─ 精读详细总结
   ↓
落盘 docs/<年月>/<日>/<id>-<slug>.md + 注册进 Sidebar（打「手动总结」标签）
   ↓
前端拿到 paper_id 后自动跳转到该纸张页（日报同一展示层渲染）
```

各阶段的作用：

| 阶段 | 作用 |
|------|------|
| 正文抓取 | 把三种输入统一成「标题 + 纯文本」供后续 LLM 使用 |
| 缓存检查 | 同一篇论文重复总结时直接返回上次结果，不再花 LLM 钱 |
| 速览五段 | DeepSeek 按 JSON 结构化输出速览卡片内容 |
| 图表抽取 | 从 PDF 里切出图片和表格存成本地资源 |
| 图表解读 | 结合图注与正文引用段落，让文本模型写出比图注更详细的中文解读 |
| 翻译 | 标题与摘要中文化，用于纸张页头部展示 |
| 精读详细总结 | 基于全文生成长篇中文精读笔记，追加为「论文详细总结」块 |
| 落盘注册 | 写 markdown、更新 `_sidebar.md`，纳入侧边栏与未读管理 |

## 输入支持哪些来源

| 来源 | 判定方式 | 处理方式 |
|------|---------|---------|
| arXiv 链接 / 裸 ID | URL 里含 `arxiv.org/abs|pdf`、`arXiv:` 或形如 `2401.12345` 的裸 ID | Atom API 拉取真实元数据（作者、发布日期等），同时下载 PDF 用于抽图；下载失败只影响图表，不阻断总结 |
| 其它网页链接 | 非 arXiv 且能解析出正文 | 正则 + HTMLParser 提取 `<title>/<h1>/<p>` 正文（页面体积上限 2MB），元数据只有标题 |
| 本地 PDF 文件 | 直接上传或拖入，上限 50MB（可用 `DPR_PDF_MAX_MB` 调整） | PyMuPDF 逐页抽全文，文件名暂作标题 |

无论哪种来源，最终抽出文本不足 20 字符都会报错提示换来源。非 arXiv 来源在
落盘时会被归一化成 `arxiv` 来源以便走统一的媒体抽取路径，且侧边栏链接会使用
你提供的原始网址（上传 PDF 则指向纸张页自身），不会被错误拼成 arxiv.org 链接。

## 每一步跑在哪里：API 还是本地模型？

| 阶段 | 跑在哪 | 说明 |
|------|--------|------|
| 正文抓取 | **本地后端进程**：urllib 直连，内置指数退避重试（覆盖 WinError 10054 连接重置等问题） | arXiv 元数据走官方 Atom API |
| 图表抽取 | **本地子进程**：PaperCropper 与 Docling 各自跑在独立子环境（Docling 用 `.venv-docling`，避免 torch 版本冲突），全链失败回退 PyMuPDF 兜底，任何一步失败都不阻断总结 | 与日报流水线共用同一套代码 |
| 速览五段 | **DeepSeek 云端 API**：JSON Schema 结构化输出，强制返回五个字段 | 与日报纸张页的速览完全一致 |
| 图表解读 | **DeepSeek 云端 API**：上下文 = 图注 caption + 正文中引用该图号的段落 + 标题/摘要，纯文本解读、不读图 | 已有解读的图表自动跳过，避免重复计费 |
| 翻译 | **DeepSeek 云端 API**：标题 + 摘要一次翻译 | |
| 精读详细总结 | **DeepSeek 云端 API**：基于全文长文生成，输出被截断时自动续写一次并以「（完）」收尾 | LLM 未配置时跳过，页面仍有骨架 |

一句话总结：**抓取和抽图都在本地完成，「理解类」工作全部交给 DeepSeek；
整条链路复用日报 Step 6，因此总结产物与日报纸张页数据结构完全同构。**

## 异步任务契约（connect.job.v1）

总结是异步 job，而不是同步 HTTP 请求（LLM 全流程可能耗时数十秒到数分钟）：

```
POST /api/paper/summarize          建 job，立即返回 job_id
GET  /api/paper/summarize/<job_id> 轮询 status + events
POST /api/paper/summarize/<job_id>/cancel  best-effort 取消
```

- job 状态机：`queued → running → completed | failed | cancelled`；
- 事件类型：`job.accepted / started / progress / completed / failed / cancelled`，
  进度事件带 `stage` 和可选 `current/total`；
- 前端每 2 秒轮询一次，按 `event_id` 去重后把新事件追加到进度列表，进度条按事件数粗略推进；
- 每个 stage 检查点都响应取消请求（如正在等 LLM 返回则在该步结束后取消）。

## 产物与副作用

1. **markdown 纸张页**：写到 `docs/<年月>/<日>/<id>-<slug>.md`
   （arXiv 用真实 ID，其它来源用标题 slug），YAML front matter 与日报纸张页同构；
2. **同名 `.txt` 全文**：作为图表解读与详细总结的引用上下文；
3. **侧边栏注册**：以「精读区」条目写入当日日期分组，打专属 `手动总结` 标签，
   不参与推荐分数统计（分数显示 `-`）；未读机制照常管理它；
4. **结果缓存**：`.local-runs/paper_summarize_cache.json`，key 为 `arxiv:<id>`
   或 `sha256:<PDF 内容哈希>`，默认最多保留 50 条（`DPR_SUMMARIZE_CACHE_MAX` 可调），
   重启本地服务缓存仍然有效。
5. **图片资源**：抽出的图表与日报论文一样落到 `docs/assets/figures/` 下对应目录。

## 触发入口与使用步骤

1. 在站内打开「📄 论文总结」页面（`#/summarize`）；
2. 任选一种输入：
   - 论文链接框贴入 arXiv / 网页链接，点「总结」；
   - 或拖入 PDF 文件（仅本地部署可见入口），点「开始总结」；
3. 页面显示分阶段进度（抓取 → 速览 → 图表 → 解读 → 翻译 → 精读总结 → 落盘）；
4. 完成后前端直接跳转到生成的纸张页，随后即可像日报论文一样阅读、
   打 1/2/3/4 阅读状态标记。

限制说明：整个功能依赖本地后端；纯 GitHub Pages 静态部署下没有后端代理，
页面会提示不可用，需先运行 `python src/local_server.py` 再刷新。

## 常见问题

- **为什么总结要在本地跑，而日报可以纯云端？**
  总结处理的是你随手丢进来的单篇站外论文——正文抓取、PDF 抽图都要现拉现算，
  这些不适合放进定时 CI；日报则是固定窗口的批处理，天然适合 GitHub Actions。
- **同一篇论文重复总结会重复花钱吗？**
  不会。命中缓存（同一 arXiv ID 或同一 PDF 内容哈希）时直接返回上次结果，
  进度里会出现一条 `cache_hit` 事件。
- **中途可以取消吗？**
  可以。「取消」按钮调用 cancel 接口，当前阻塞中的 LLM 调用会在该阶段结束后停止，
  已产生的局部产物不会回滚。
- **总结出的论文会出现在首页/日报统计里吗？**
  不会计入推荐名额与评分统计，只作为一张普通纸张页挂进 Sidebar 当日分组、
  带「手动总结」标签，方便你在侧边栏里找到它。
- **为什么这篇总结没有图表解读？**
  三种可能：arXiv PDF 下载失败、该论文本身几乎没有可抽取的图表、
  或者 LLM 配置缺失导致解读环节被跳过——前两者不影响文字部分正常产出。
- **非 arXiv 的网页链接总失败？**
  一些站点做了反爬或正文全部动态渲染，HTML 解析拿不到足够文本；
  这类论文建议直接上传 PDF。
